# Проект настольного CapCut

## Первое подключение проекта

1. Пользователь создаёт новый пустой проект в приложении CapCut и сообщает его уникальное имя или полный путь. Загрузки в облако и входа через CapCut MCP здесь нет.
2. Найди путь через desktop.mjs projects. Если CapCut хранит проекты в другом месте, укажи --drafts DIR (каталог с root_meta_info.json). Не угадывай проект по дате и не создавай поддельный новый проект из чужого заполненного.
3. desktop.mjs inspect-project --project DIR читает структуру. Адаптер принимает открытый JSON формата 360000 со схемами 185.0.0, 189.0.0, 191.0.0. Это проверка структуры, не гарантия совместимости каждой сборки. После обновлений нужен короткий пробный проект. Зашифрованные проекты не изменяются.
4. Подготовь plan/prepare/render до запроса действия пользователя. Когда требуется запись, попроси сохранить работу и полностью закрыть CapCut. Насильственно закрывать процесс нельзя. Не задавай повторный вопрос о разрешении записи, если выбранный новый проект уже предназначен пользователем для монтажа.

## Запись

    node "<S>/scripts/desktop.mjs" stage --job "<J>" --project "<ПОЛНЫЙ ПУТЬ ПРОЕКТА>"
    node "<S>/scripts/desktop.mjs" apply --job "<J>" --project "<ТОТ ЖЕ ПУТЬ>"
    node "<S>/scripts/desktop.mjs" check --project "<ТОТ ЖЕ ПУТЬ>"

stage создаёт native-stage.json в папке ролика; проект пока не изменяет. План, материалы и целевые файлы проверяются. При apply проверяется, что CapCut закрыт, проект/индекс с момента stage не изменились и подготовленные медиа соответствуют плану. Перед записью резервируются все затрагиваемые файлы, включая root_meta_info.json при наличии.

Синхронизируются существующие draft_content.json, Timelines/ID/draft_content.json и template-2.tmp, а также метаданные и запись в индексе. Записи заменяются пофайлово; при ошибке уже изменённые файлы откатываются, если не изменены третьей стороной. Это не глобальная файловая транзакция и не гарантия при отключении питания: сохраняется журнал backups/ID/transaction.json.

Повторная сборка разрешена для своего проекта с теми же хешами файлов. Ручные изменения в CapCut вызывают отказ. Сохрани их, проанализируй текущую версию и согласуй конкретный способ объединения либо используй новый пустой проект. Не отключай проверку и не подменяй сохранённые хеши для обхода.

## Открытие и экспорт

После apply попроси открыть проект в настольном CapCut и проверить короткий участок: расположение головы, текст, альфа, звук, отсутствие пропавших файлов. Если доступно разрешённое управление Windows, можно проверить через него; браузерный инструмент сам по себе приложением ПК не управляет.

Никакой команды запуска приложения или выдуманного CapCut export CLI комплект не использует. Для native-экспорта открой проект, выбери экспорт 1080×1920, H.264, FPS проекта, качественный битрейт, AAC; проверь полученный файл через reel.mjs verify. Не называй этап завершённым до появления MP4.

Если интерфейс недоступен, локальный render подготовит MP4 по тому же плану. Отчёт различает: файлы проекта записаны / проект открыт и проверен / native-экспорт / локальный рендер. У локальной и native-версии могут отличаться текст и конечный микс.

## Откат

    node "<S>/scripts/desktop.mjs" restore --job "<J>"

Возвращает файлы последнего apply только при закрытом CapCut и точном совпадении текущих хешей с записанными. Если CapCut уже пересохранил проект или изменился общий индекс, автоматический откат остановится. Не копируй старый общий индекс поверх новых проектов. Для ручного восстановления сначала прочитай transaction.json и сравни текущие изменения.

Файлы prepared/, graphics/, audio/ и generated/ не удалять и не перемещать после сборки: CapCut ссылается на них по абсолютным путям. Копия всей папки проекта сама по себе не делает исходные пути переносимыми. Для переноса на другой ПК перепривяжи медиа и проверь проект.
